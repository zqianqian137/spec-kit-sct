## Outline

1. Read `.specify/feature.json` to get the feature directory path.

2. **Load context**: `.specify/memory/constitution.md` and `<feature_directory>/spec.md` and
   `<feature_directory>/plan.md` and `<feature_directory>/tasks.md`.

3. **(SCT) Ensure the SoT exists**: confirm `<feature_directory>/acceptance.yaml` is present.
   - If missing, run `speckit.sct.merge` first (it auto-discovers `spec.md`, `plan.md`,
     `data-model.md`, `api-contracts.md` in the feature directory).
   - This SoT is the implementation contract — code against the APIs/rules/scenarios it lists.

4. **(SCT) Generate tests before coding**: run `speckit.sct.codegen` against `acceptance.yaml`
   to derive the write-once test stubs (api / rule / scenario). Generated tests are not
   hand-edited; they are regenerated by `sct.codegen` on later changes.

5. **Execute tasks** in order:
   - Complete each task before moving to the next
   - Mark completed tasks by changing `- [ ]` to `- [x]` in `<feature_directory>/tasks.md`
   - Halt on failure and report the issue

6. **Validate**: verify all tasks are completed and the implementation matches the spec and the
   SoT.

7. **(SCT) Post-implementation hooks** fire automatically on `after_implement`:
   - `speckit.sct.impact` — reverse-traces the code just written to the affected spec scenarios
     (tier gate: L1 fast path skips the rest).
   - `speckit.sct.check` — three-way consistency check (spec ↔ code ↔ test) and triggers any
     deferred test generation.
   Do not run these manually; they are wired by the sct extension's `after_implement` hook.
